Choosing the Right Sharing Method

▶

When you finish building a course in PreseMaker, one of the most important decisions you face is how to get that content to the people who need it. PreseMaker offers five distinct sharing and distribution methods, and each one is designed with a different workflow, audience, and technical context in mind. Choosing the wrong method for your situation can mean extra friction for learners, unnecessary complexity for you, or content that simply does not reach its intended audience. Understanding what each method does — and what it does not do — is the foundation for making that choice confidently.

The five primary methods are version control (git), GitHub Pages, the course repository service, archive export, and iFrame embedding. They differ across several key dimensions: where course files are physically stored, who can access the content and under what conditions, what technical steps are involved, and how well the method supports ongoing collaboration or future reuse. A helpful way to think about these dimensions before diving into each method is to see them side by side.

GitHub Pages Public web publishing Yes Yes Shareable public URL for learners
Course Repository Service Community sharing and reuse Yes Yes (within educator community) Sharing with or borrowing from other educators

Version control through PreseMaker's git integration is the method to reach for when your primary concern is the safety and history of your course files during development. Every time you commit your work, PreseMaker records a snapshot of the course at that point in time. This means you can review what the course looked like at any earlier stage, roll back changes that introduced problems, and maintain a remote backup so that a lost or broken local machine does not mean lost work. You can also push updates to a remote repository and pull the latest version onto a different machine, which makes version control well suited for collaborative course development where more than one person is contributing changes.

A critical point that surprises many new users is that version control alone does not make your course accessible to learners. A git repository stores files; it does not serve them as a website. Think of it like saving a Word document to a cloud drive — the file is backed up and can be shared with collaborators who have access, but a learner cannot simply navigate to a URL and read it. Version control is a development and safety workflow, not a distribution channel. Importantly, PreseMaker manages all of this internally — you do not need to open a terminal or know any git commands to take advantage of it.

GitHub Pages is the natural companion to version control when you want learners to access course content through a browser. Once you connect PreseMaker to your GitHub account and enable GitHub Pages for your course repository, PreseMaker handles the publishing process automatically. The repository continues to store your files the way it always did, but GitHub Pages additionally serves those files as a live website at a public URL that you can share with anyone. No manual configuration on the GitHub website is required — PreseMaker abstracts away those setup steps.

Because GitHub Pages builds on top of the git repository, both methods work together seamlessly: you develop and track changes using version control, and when you are ready to publish an update, GitHub Pages reflects those changes publicly. This pairing is one of the most common workflows in PreseMaker for courses intended for a general online audience. The result is a permanent, linkable URL that learners can bookmark and revisit, and that you can embed in email communications, syllabi, or social media.

The course repository service serves a different purpose than hosting a website for learners. Its audience is primarily other educators. When you publish a course to the repository service, you are making it available for colleagues or fellow educators to discover and import directly into their own PreseMaker installations — not just to view it in a browser. Equally, if you are looking for materials to build on rather than creating everything from scratch, the repository service lets you browse and import courses that others have shared.

This focus on reusability and community distribution sets the course repository service apart from GitHub Pages. GitHub Pages is about giving learners a URL; the repository service is about enabling educators to adapt, remix, and build upon shared materials. If you are part of a professional learning community, a faculty group, or an open education initiative, the course repository service is the most direct path to that kind of collaborative content ecosystem.

Archive export steps away from all cloud and internet-based workflows entirely. When you export a course as an archive, PreseMaker packages the course files into a single portable file that you can transfer directly — by email attachment, USB drive, shared network folder, or any other file-transfer method you prefer. The recipient then imports that archive into their own copy of PreseMaker to access the course. No GitHub account is needed, no internet connection is required for the transfer itself, and no third-party service is involved.

This makes archive export ideal for controlled or closed distribution scenarios: sharing a course with a specific colleague who is not connected to your GitHub organization, moving your course from an old machine to a new one, distributing materials in an environment with restricted or unreliable internet access, or providing a snapshot of course materials at a particular point in time without ongoing live updates. The trade-off is that the archive is a static package — changes you make later are not reflected in the exported file unless you export again and redistribute.

iFrame embedding is the right choice when learners should experience your course within a platform they are already using rather than navigating to a separate URL. Many learning management systems, website builders, wikis, and internal intranets support HTML iFrames, which allow content from another URL to appear as an embedded panel inside the host page. PreseMaker generates an embed code snippet that you copy and paste into any platform that accepts raw HTML.

An important prerequisite is that iFrame embedding requires the course to already be hosted somewhere accessible on the web — the iFrame simply displays content from another URL, so that URL must exist and be reachable. In practice this means iFrame embedding almost always pairs with GitHub Pages: you publish the course publicly via GitHub Pages to get a URL, and then use that URL in the iFrame embed code to display the course inside your LMS or website. On its own, iFrame embedding is not a hosting solution; it is an integration layer that sits on top of one.

Pulling all five methods together, the decision process becomes much cleaner when you start from your use case rather than from the tools themselves. Ask yourself a few guiding questions:

  • Is my main concern tracking changes and protecting my work during development? If yes, start with version control. You can always layer additional sharing methods on top later.
  • Do I want learners to access the course through a browser via a public URL? GitHub Pages is the right choice, and it pairs naturally with version control you may already be using.
  • Am I trying to share materials with other educators, or looking to build on someone else's work? The course repository service is built precisely for that kind of community reuse.
  • Does the recipient have no cloud account, limited internet access, or do I need a clean one-time handoff? Archive export handles this without any dependencies on external services.
  • Do my learners live inside a specific platform — an LMS, a company intranet, a course portal — and should the content appear there rather than in a separate tab? Use iFrame embedding, and make sure the course is hosted (typically via GitHub Pages) before generating the embed code.

It is also worth noting that these methods are not mutually exclusive. A well-developed course might use version control throughout its creation, publish via GitHub Pages for the primary learner audience, and be shared as an archive with a partner institution that does not use GitHub. Understanding each method as a distinct tool with a specific strength — rather than treating them as alternatives where only one can be used — gives you the flexibility to serve multiple audiences and contexts with the same underlying course.
