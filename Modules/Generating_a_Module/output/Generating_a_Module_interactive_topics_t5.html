Course and Module Storage as Folders on Disk

▶

When you work inside PreseMaker, everything you see on screen — your courses, your modules, your slides, your media — has a direct, one-to-one counterpart sitting on your computer's file system as ordinary folders and files. This is not an abstraction or a hidden database: the storage model is a transparent folder hierarchy that mirrors the logical structure you interact with inside the application. Understanding how this hierarchy is organized is essential for anyone who wants to manage course content confidently, collaborate with others, recover from problems, or simply know where their work actually lives.

The design philosophy behind folder-based storage is straightforward: keep things visible, portable, and compatible with the tools people already know. Rather than locking content inside a proprietary binary file or an opaque database that only the application can read, PreseMaker places every asset, every configuration file, and every piece of generated content into a conventional directory tree that any operating system can browse, copy, compress, or search. This section walks through every layer of that hierarchy in depth.

Courses as Top-Level Folders

The outermost container in the hierarchy is the course folder. When you start a new course in PreseMaker, the application immediately creates a dedicated folder on disk to hold everything related to that course. You do not have to create this folder manually — PreseMaker handles it automatically the moment you confirm the new course. The folder name is derived from the course title you assign inside the application, so if you name your course Introduction to Data Privacy, PreseMaker will create a folder with a corresponding name such as Introduction to Data Privacy (or a filesystem-safe variant of it) in the location you specified during setup.

Everything that belongs to that course — every module, every media file, every setting, every piece of generated output — lives inside this one top-level folder. There is no situation in which part of a course is stored elsewhere while the rest remains here; the course folder is self-contained by design. This means that to move a course to a different drive, share it with a colleague, or archive it for safekeeping, you only ever need to work with that single folder. Copy it, compress it, move it — the entire course travels with it.

A practical consequence of this design is that the course folder's location on your machine is the single most important path to remember. If you need to back up your work, you back up that folder. If you need to hand the project to someone else, you hand them that folder. The application itself is separate from the content; the course folder is the course.

Modules as Subfolders Within the Course Folder

Inside the course folder, each module is represented by its own subfolder. When you create a module in PreseMaker, the application creates that subfolder immediately. When you delete a module, the application removes it from the course structure. The folder name for each module is derived from the module's name at the time it is created and is designed to remain stable — meaning it does not automatically change if you later rename the module in the interface.

This stability is intentional and important. Content files inside a module subfolder — slides, media references, configuration data — contain paths and references that point to other files using the folder name as part of the address. If renaming a module caused the underlying folder name to change, every one of those internal references would break simultaneously. Instead, PreseMaker separates two distinct concepts:

  • Display name: the human-readable label you see on screen when you work with the module. This can be changed freely through the application, and the change is saved into the module's metadata file.
  • Folder name: the actual directory name on disk, which acts as a stable identifier. It is set when the module is first created and does not change when you rename the module.

For example, imagine you create a module called Module 1 – Overview. PreseMaker creates a subfolder named something like Module_1_Overview. Later you decide the module should be called Getting Started. Inside PreseMaker you rename it, and the display name updates immediately everywhere in the interface. But on disk, the folder is still named Module_1_Overview, and every file path that pointed into that folder continues to work without modification.

Module order within a course is handled the same way: it is tracked in metadata, not encoded in folder names. If you have five modules and drag the third one to the first position, the folders on disk do not change their names or move — only the ordering information recorded in the course's configuration is updated. This means folder names are never prefixed with numbers like 01_, 02_, and so on, because such a scheme would require renaming folders every time you reorder content.

Relationship Between On-Screen Structure and File Hierarchy

The visual structure you see in PreseMaker's interface is a direct reflection of the folder hierarchy on disk, but the relationship has important nuances depending on the type of change you make. The table below summarizes how each common operation maps to what happens on disk:

Action in PreseMaker Effect on Disk Effect on Metadata
Create a new module New subfolder created inside the course folder Module entry added to course configuration
Delete a module Module subfolder removed from the course folder Module entry removed from course configuration
Rename a module No change to folder name Display name updated in module metadata
Reorder modules No change to folder names or positions Order values updated in course configuration
Add content to a module Files written into the module's subfolder References updated in module metadata

The critical implication of this design is that PreseMaker expects to be the sole manager of the folder hierarchy. If you use your operating system's file explorer or a terminal to manually rename a module subfolder, move it, or delete files within it without going through PreseMaker, the application's metadata will still contain the old folder name. The next time you open the course, PreseMaker will look for a folder that no longer exists at the expected path, and the affected module will appear broken, empty, or missing entirely.

This does not mean the folder structure is fragile — it means the structure should be modified through the application, which keeps the metadata and the file system synchronized. However, knowing that the folder structure is transparent and human-readable is a powerful troubleshooting tool: if something looks wrong on screen, you can open the course folder, inspect what is actually there, and compare it with what PreseMaker expects. In many cases, a missing module that looks like a catastrophic failure is simply a folder that was accidentally moved, which can be corrected by moving it back.

Contents Stored Inside a Module Subfolder

Each module subfolder contains several categories of files, each serving a distinct purpose in how PreseMaker reads and displays the module:

  • Source material files: the raw content you authored or imported for the module — text, outlines, scripts, or other input that forms the basis of the module's learning material.
  • Generated topic content: the output that PreseMaker produces from source material, stored as structured files the application reads to render slides, pages, or other deliverable formats.
  • Module configuration data: a metadata file (or set of files) that records the module's display name, its order within the course, its settings, and references to all the content and assets it uses. This is the file PreseMaker consults first when opening a module.
  • Asset subdirectories: dedicated folders within the module subfolder that hold media referenced by the module — images, documents, audio clips, or video files. Keeping assets in a predictable location inside the module subfolder means that when the entire course folder is moved or shared, the relative paths from configuration files to assets remain valid without any path updates.

Every time you open a module in PreseMaker, the application reads these files fresh from disk. There is no persistent in-memory cache that might show you a stale version of the content — what you see on screen is always a reflection of what is currently stored in the subfolder. This makes the storage model highly reliable: saving your work means the files are updated on disk immediately, and reopening the module or restarting the application will always show the latest saved state.

Practical Benefits of the Folder-Based Storage Model

The decision to use a transparent folder hierarchy rather than a proprietary database has a range of concrete, everyday advantages that become apparent as soon as you start managing real course content at scale.

  • Simple sharing and collaboration: Because the entire course is a single top-level folder, sharing it requires nothing more than copying or compressing that folder and sending it to a collaborator. There are no export steps, no special archive formats to create, and no import wizards on the receiving end — the recipient simply places the folder in their PreseMaker courses directory and opens it.
  • Compatibility with version control: Tools like Git, which are standard in software development for tracking changes over time, work naturally with folder trees full of text-based files. A PreseMaker course folder can be initialized as a Git repository, giving course authors a full history of every change made to every file, the ability to revert to any previous state, and the ability to merge contributions from multiple authors using branching workflows.
  • Backup utilities work without configuration: Any backup tool — whether a simple scheduled copy, a cloud sync service like Dropbox or OneDrive, or an enterprise backup system — will correctly back up a PreseMaker course folder because it is just a folder. There is no need to schedule database exports or use application-specific backup commands.
  • File system search finds content directly: Because content is stored as readable files rather than inside a binary database, operating system search tools can locate specific text, file names, or media assets across an entire course instantly. If you need to find every module that references a particular image file, a simple file system search will surface it.
  • Content recovery is straightforward: If a module becomes corrupted or content is accidentally deleted, recovery does not require specialized database repair tools. You can restore individual files from a backup, inspect the configuration metadata in a text editor to understand what is missing, or reconstruct the folder structure manually. The human-readable nature of the storage format means the content is never locked away in an inaccessible form.
  • Reduced vendor lock-in: A folder of readable files is inherently more portable than proprietary binary formats. Even if circumstances required migrating away from PreseMaker in the future, the underlying content — text, images, documents — would remain accessible and usable.

Together, these benefits make the folder-based storage model a practical and resilient foundation for course authoring. The more clearly you understand how the on-screen structure maps to folders and files on disk, the more confidently you can manage, protect, share, and troubleshoot your course content.
