API Key Encryption and Local Storage

▶

When you add an API key to PreseMaker, you are entrusting the application with a sensitive credential that grants direct access to a paid AI service. Understanding exactly where that key lives, how it is protected, and what happens to it during normal use is essential for making an informed decision about your own security posture. PreseMaker is designed from the ground up around a local-first, encryption-backed approach to key storage — meaning the application deliberately avoids the most common pitfalls that have led to API key leaks in other software products.

What Is Local Storage for API Keys?

Local storage, in this context, means that your API key is saved exclusively on the device where PreseMaker is installed. There is no account system, no cloud sync, and no remote database involved in holding your key. When you type your key into the Settings screen and save it, that credential is written to an encrypted store that exists only within your device's file system — it never travels to a PreseMaker server, a cloud backup service managed by PreseMaker, or any other external destination as part of the saving process itself.

This has one important practical consequence: because the key is tied to a specific installation on a specific device, it does not survive actions that destroy or reset that installation. If you uninstall PreseMaker, perform a factory reset, or wipe the application's data through your operating system, the stored key is gone with it. The application cannot recover it for you because it was never stored anywhere else. For this reason, you should always maintain your own personal record of each API key — for example, storing it in a dedicated password manager such as 1Password, Bitwarden, or the password manager built into your operating system. Think of PreseMaker's local storage as a convenience cache, not a backup vault.

How Encryption Protects Your API Keys

Storing data locally is only half of the protection story; the other half is encryption. PreseMaker does not write your API key to disk as plain readable text. Instead, the key is encrypted before it is written to storage, so the file that actually sits on your hard drive or SSD contains an unreadable ciphertext representation of your key rather than the key itself.

To understand why this matters, consider what happens if someone with physical or remote access to your device opens the folder where PreseMaker keeps its application data and reads the storage file directly. Without encryption, they would see your key immediately. With encryption, they see something like a block of random-looking characters that is computationally infeasible to reverse without the correct decryption key. The attacker gains nothing actionable.

Crucially, this entire process is automatic and invisible to you as the user. You do not need to create a master password, manage a certificate, or perform any extra steps. When you save a key, encryption happens in the background before the data touches the disk. When PreseMaker needs to use the key to call an AI provider, decryption happens in the background in memory, just in time for the network request. You never handle the raw key again after the initial entry.

This protection applies uniformly across all AI providers that PreseMaker supports:

  • Anthropic Claude — keys for accessing Claude models are encrypted and stored locally under the same scheme.
  • Google Gemini — your Gemini API credentials receive identical treatment.
  • OpenAI — OpenAI keys, which are among the most sensitive due to the wide range of services they can access, are fully encrypted at rest.
  • Mistral — Mistral API keys are covered by the same local encryption approach.

There is no tiered or partial protection — every supported provider's key is encrypted in exactly the same way.

Why PreseMaker Does Not Store Keys on a Server

Many applications that integrate with third-party APIs take a server-side approach: the user submits their key, the application stores it in a remote database, and the application's backend makes API calls on the user's behalf. This architecture has legitimate engineering advantages — it simplifies session management and enables features like cross-device sync — but it introduces a serious security risk. If that server is breached, every key stored in that database is potentially exposed simultaneously. High-profile breaches of SaaS companies have repeatedly demonstrated that this is not a theoretical concern.

PreseMaker's architecture eliminates this entire class of risk by design. Because no PreseMaker server ever receives your API key, there is no PreseMaker server database of keys that could be stolen. A security incident affecting PreseMaker's infrastructure — its website, its update servers, its analytics pipeline — cannot expose your API key because that infrastructure simply does not have it.

This design also closes a subtler risk: accidental third-party exposure. Server-side applications often integrate logging tools, error tracking services, performance monitoring platforms, and analytics providers. A misconfigured logger can inadvertently capture an API key that appears in a request header or body and ship it off to a third-party observability service. Because PreseMaker's server never sees your key, none of these downstream integrations can see it either. Your key's journey begins and ends on your own device and the AI provider's servers.

Addressing Common Privacy Concerns

A natural question when any application asks you to store a sensitive credential is: could this application use my key without my knowledge? With PreseMaker's local architecture, the answer is no — and here is why.

Since the encrypted key lives only on your device, the only software that can decrypt and use it is PreseMaker running on that device, in an active session initiated by you. PreseMaker running on its own servers cannot access your key because, again, the key is not there. There is no pathway for PreseMaker as a company to silently make API calls on your behalf, bill usage to your account, or harvest your key for other purposes.

The only moment your key leaves your device in any form is when you actively trigger content generation inside PreseMaker. At that point, the decrypted key is included in a standard API request sent directly to the relevant AI provider — for example, a request to api.openai.com for an OpenAI key, or to api.anthropic.com for a Claude key. That transmission is protected by the provider's own TLS/HTTPS connection, the same encryption technology that protects online banking and e-commerce. No PreseMaker-controlled intermediary sits between your device and the provider's API endpoint.

You also retain complete control over the lifecycle of your stored key. At any point, you can navigate to the Settings screen, delete the stored key, or replace it with a different one. The following table summarizes where control sits for each aspect of the key's lifecycle:

Action Who Controls It Where It Happens
Saving a new key User PreseMaker Settings screen, on your device
Encrypting the key at rest PreseMaker (automatic) Your device's local storage
Decrypting and using the key PreseMaker (only when you generate content) Your device's memory, during your active session
Transmitting the key to the AI provider PreseMaker (triggered by your action) Direct HTTPS connection to the provider's API
Deleting or replacing the key User PreseMaker Settings screen, on your device
Revoking the key entirely User AI provider's own dashboard (e.g., platform.openai.com)

User Responsibilities for Key Security

Encryption and local storage are powerful safeguards, but they operate at the software and storage layer. There are real-world scenarios at the physical and social layer that no software design can fully prevent, and users share responsibility for guarding against them.

The most direct risk is shared device access. Because PreseMaker can decrypt and use your stored key for anyone who opens the application on your device, anyone with physical or remote access to your device and the ability to launch PreseMaker can potentially trigger API calls that will be billed to your account. This does not require them to know or see your key — they simply need to be able to use the app. You should therefore avoid leaving PreseMaker installed and your key saved on devices that untrusted individuals can access. If you share a computer with others, consider deleting your stored key when you are finished with a session, or using operating-system-level access controls (separate user accounts, screen locks) to prevent unauthorized use.

If you ever have reason to believe your key may have been exposed — whether through a lost device, a suspected malware infection, or any other circumstance — the correct response is to revoke the key immediately through the AI provider's own dashboard. Revocation at the provider level is the definitive action: it invalidates the key everywhere, regardless of where it might be stored or who might have a copy. After revoking, generate a fresh key and add the new one to PreseMaker. The steps for reaching the revocation dashboard vary by provider:

  • OpenAI: Visit platform.openai.com, navigate to API keys, and delete the compromised key.
  • Anthropic Claude: Visit console.anthropic.com, go to API Keys, and revoke the key.
  • Google Gemini: Visit aistudio.google.com or the Google Cloud console, navigate to your API credentials, and disable or delete the key.
  • Mistral: Visit console.mistral.ai and manage your keys from the API Keys section.

Finally, make a habit of regularly reviewing your API provider's usage dashboard. Each provider offers a usage or billing page showing how many tokens or requests have been made against your key, often broken down by time period. Monitoring this dashboard is the most reliable way to detect unauthorized use early — before it results in a large unexpected bill. If you see usage that does not correspond to your own activity in PreseMaker or any other tool you use, treat it as a signal of compromise and revoke immediately. Many providers also allow you to set spending limits or usage alerts, which can serve as an automatic early-warning system.
