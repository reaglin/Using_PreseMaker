Keeping the Course Website Current

▶

Once a course is built in PreseMaker, the work of keeping it accurate and accessible does not end at the first publish. Every course website is a living document — modules are revised, media is updated, topics are added or removed, and small corrections accumulate over time. The published website, however, does not update itself automatically. It reflects only what was generated the last time the publish process was run. Understanding this relationship between the source content and the live site is the foundation of effective course maintenance, and it shapes every decision about when, how, and how often to re-publish.

Understanding Why Re-Publishing Is Necessary

PreseMaker's publish feature works by reading the current state of the course's source content and generating HTML output from it. The central artifact produced for each module is its HTML index — the landing page that organizes and presents that module's material to learners. When you edit a module's text, swap out an image, reorganize topics, or adjust metadata, those changes exist only in the source. The HTML index that learners actually browse has not changed at all until the publish process is run again.

This distinction — between the source content and the generated output — is critical. Think of PreseMaker's publish function as a compiler or a static site generator: the source files are your editable inputs, and the HTML output is the compiled result. Just as recompiling source code is required to produce an updated executable, re-publishing in PreseMaker is required to produce an updated website. Skipping re-publication after edits means the live website will display stale or incorrect information, potentially confusing learners who encounter content that contradicts what an instructor has just corrected or updated.

Re-publishing also ensures synchronization across the entire site. A course website is not just a collection of independent pages — the module indexes, navigation elements, and the top-level site structure are all interrelated. When one module's content changes, re-publishing regenerates that module's HTML index so that it accurately reflects the new material, keeping the browsable site and each module's landing page fully synchronized with the source.

Identifying When to Re-Publish

Knowing when to re-publish is just as important as knowing how. Not every save or minor draft edit demands an immediate re-publish, but certain categories of change make re-publishing both necessary and urgent.

  • Text, media, or structural changes within a module: Any time you modify the wording of a learning objective, replace an outdated diagram, reorder subtopics, or correct a factual error inside a module, re-publishing is required so those corrections appear on the live landing page.
  • Adding or removing entire modules: These are the most consequential changes. Adding a new module means the top-level course navigation must include it; removing one means dead links or references to nonexistent content could appear. A full site re-publish is mandatory in both cases so that the navigation and index accurately reflect the new course structure.
  • Metadata and cosmetic updates: Changes that might seem trivial — updating a module's display title, adjusting a description field, correcting a date — can still affect the generated HTML index if PreseMaker pulls that metadata into the rendered output. These changes also require re-publishing to appear correctly on the site.

A useful rule of thumb is to treat the published website as a deliverable, not a draft. Any change that you would want a learner to see is a change that requires re-publishing before it reaches them.

The Re-Publishing Workflow in PreseMaker

The mechanical process of re-publishing in PreseMaker is straightforward, but understanding each step helps you avoid common missteps and ensures the resulting site is complete and correct.

  • Step 1 — Open the course: Launch PreseMaker and open the course project you have been editing. Confirm that you are working on the correct course file, especially in environments where multiple course projects exist side by side.
  • Step 2 — Navigate to the publish feature: Locate and open PreseMaker's publish panel or publish dialog. This is the interface through which you initiate the regeneration process.
  • Step 3 — Initiate the publish run: Start the publish process. During this run, PreseMaker reads each module's current source content and regenerates its HTML index, capturing all text edits, media changes, structural reorganizations, and metadata updates that have occurred since the last publish.
  • Step 4 — Allow full completion: Let the process run to completion without interrupting it. Stopping a publish run partway through can leave some module indexes regenerated while others remain on their previous version, creating an inconsistent site where different modules reflect different states of the content.
  • Step 5 — Retrieve and distribute the output: Once PreseMaker confirms the publish is complete, the full browsable website has been rebuilt and is ready for distribution to learners or deployment to a hosting environment.

Managing Multiple Modules During Updates

In a course with many modules, keeping track of which modules have been touched since the last publish is an important discipline. Without that awareness, it is easy to re-publish under the assumption that only one module has changed, only to discover later that edits to two other modules were also pending and were either included accidentally or overlooked entirely.

The safest and most reliable approach when several modules have been updated simultaneously is to re-publish the entire course at once. This guarantees that every HTML index is regenerated from its current source, eliminating any risk of partial or inconsistent updates. The slight additional time cost of a full re-publish is almost always worth the certainty it provides.

If your workflow requires tracking which modules need attention, a simple log can help. The table below illustrates a lightweight tracking format that a course developer might maintain alongside their editing work:

Module Type of Change Date Modified Re-Published?
Module 1: Introduction Updated learning objectives text 2025-06-01 Yes — 2025-06-01
Module 3: Core Concepts Replaced diagram image 2025-06-03 No — pending
Module 5: Assessment Added new subtopic section 2025-06-03 No — pending
Module 7: Wrap-Up Corrected broken link in text 2025-06-04 No — pending

After re-publishing, go back through each module's HTML index to verify that the latest content is correctly reflected. This post-publish check is a brief but important habit — it confirms that the publish process captured all intended changes and that nothing was inadvertently left in its prior state.

Verifying the Updated Course Website

Re-publishing regenerates the site, but verification confirms that the regeneration was successful and complete. Skipping this step is one of the most common sources of course maintenance errors, because it allows problems introduced during the re-publish to go unnoticed until learners encounter them.

A thorough verification pass covers several areas:

  • Content accuracy: Browse to each module that was modified and read through its HTML index. Confirm that the edits you made in the source are now visible in the rendered output exactly as intended. Pay particular attention to text corrections, reordered sections, and newly added content.
  • Media integrity: Check that images, videos, audio files, and downloadable assets load correctly on every affected page. A re-publish can sometimes expose path issues or missing files that were not apparent in the source editor.
  • Navigation and links: Click through the course's navigation elements to confirm that all module links resolve correctly. If modules were added or removed, verify that the navigation reflects the new structure and that no links point to pages that no longer exist.
  • Layout and formatting: Scan each updated page for visual anomalies — broken layouts, misaligned elements, or formatting that did not render as expected. These issues can arise if source content contains formatting that the HTML generator interprets differently than intended.

If any issues are found during verification, correct them in the source and re-publish the affected modules before making the site available to learners.

Establishing a Maintenance Cadence

Ad hoc re-publishing — doing it whenever someone remembers — leads to inconsistency. Some updates reach learners quickly; others sit in the source for weeks before being published. Defining a deliberate publishing cadence removes this unpredictability and builds reliable habits into the development workflow.

Common cadence models include:

  • After every editing session: The most conservative approach. Every time a developer finishes a working session, they re-publish before closing the project. This keeps the live site perpetually current but may involve many small publish runs.
  • At the end of each development sprint: In team environments that use sprint-based workflows, re-publishing at sprint completion aligns the live site update with the natural rhythm of work. Stakeholders know that the site will reflect the sprint's output once the sprint closes.
  • On a fixed schedule: Some teams re-publish on a set day each week or at the end of each month. This is straightforward to communicate and easy to plan around, though it means updates made early in the cycle may not reach learners until the next scheduled publish.

Whichever cadence you choose, communicate it clearly to stakeholders — instructional designers, subject matter experts, reviewers, and learners where appropriate — so everyone understands when to expect the live site to reflect recent changes. Misaligned expectations about the publish cycle are a frequent source of confusion and unnecessary escalation.

Beyond responding to edits, consider scheduling periodic full re-publishes even during quiet periods when no significant changes have been made. Over time, subtle drift can develop between the source content and the published output due to tooling updates, environment changes, or minor inconsistencies that accumulated across many small publish runs. A periodic full re-publish from scratch resets that baseline, ensuring that what learners see is a clean, accurate rendering of the current source content.
