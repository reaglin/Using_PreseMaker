Introduction to PreseMaker's Publish Feature

▶

When a course is built in PreseMaker, the work of authoring individual modules and the work of making those modules available to learners are treated as two distinct phases. The publish feature bridges those phases. It is the mechanism that takes every module an author has built, draws them together, and outputs a fully navigable website that learners can browse without any additional setup or manual configuration. Understanding what the publish feature does, how it relies on each module's HTML index, and why it performs a content refresh before assembly will help authors use it confidently and avoid the most common publishing pitfalls.

At its core, the publish feature is an automated assembly tool. When an author works on a course in PreseMaker, the modules that make up that course exist as individual units — each with its own content files, media assets, and structural data. Left in that state, the modules are not yet woven together into anything a learner could navigate. The publish feature solves this by scanning all of the modules belonging to a course, collecting their component files, and organizing everything into a structured website format. The output is a coherent site where a learner can move from one module to the next through a consistent navigation layer, without ever needing to open a file manager or type a file path.

This automation matters because manually linking multiple modules is both tedious and error-prone. Consider a course with a dozen modules: an author who tried to build the navigation by hand would need to create and maintain links between every module's starting page, ensure that every link pointed to the correct relative path, and update all of those links whenever a module was added, removed, or renamed. A single broken path can leave a learner stranded on a page with no way forward. The publish feature removes that entire category of risk by handling the linking and arrangement programmatically, applying the same logic every time regardless of how many modules are involved.

The published result is not simply a flat list of files dropped into a folder. The feature organizes modules into a structured website format, meaning the output respects a predictable hierarchy that browsers can render and learners can navigate. This structure is what makes the site browsable — learners move between modules through interface elements rather than through improvised file access, and the experience feels like a single cohesive course rather than a loose collection of documents.

Central to how the publish feature constructs this navigable structure is the concept of each module's HTML index file. Every module in PreseMaker contributes exactly one HTML index file to the published site. This file acts as the dedicated starting page for that module — the page a learner lands on when they enter the module for the first time, and the page that the site's navigation system points to when it links to that module from elsewhere in the course.

The publish feature treats these index files as anchor points. When it builds the site's navigation structure — the menus, breadcrumbs, or sequential controls that let learners move between modules — it uses each module's index file as the target for that module's entry. This design keeps the navigation logic simple and reliable: instead of trying to determine which of a module's many internal pages should be the entry point, the system always defers to the index. As a result, if a module's index file is missing, malformed, or saved under an unexpected name, the publish feature cannot correctly anchor that module into the navigation, and learners may find it unreachable or broken in the published site.

This is why ensuring that each module has a properly formed HTML index is treated as a prerequisite rather than an optional detail. A properly formed index means the file exists, carries valid HTML structure, and is located where the publish feature expects to find it. Authors who rename index files, move them into subdirectories, or accidentally delete them during editing will encounter navigation gaps in the published output. Checking for a well-formed index in every module before initiating a publish is a straightforward habit that prevents a disproportionate number of post-publish problems.

Before the publish feature assembles the site, it performs a content refresh on every module. This step is triggered automatically when publishing begins — authors do not need to run it separately. The purpose of the refresh is to ensure that the version of each module captured in the published site reflects the most recent edits, not an earlier cached or saved state.

To understand why this matters, consider the workflow of a typical course update. An author might open a module, revise several pages, add a new activity, and save the changes. Without a refresh step, the publish process might assemble the site using a previously processed version of that module's content — one that predates the recent edits. The learner would then see the old material even though the author's working files contain the updated version. The content refresh eliminates this risk by processing each module's current state immediately before the assembly begins, so the files that go into the site are guaranteed to match what the author last saved.

The refresh step also enforces consistency across the entire course. Because it runs against all modules at the same time — not just the ones an author remembers editing — it catches cases where a module was modified indirectly, such as when shared assets or template changes cascade across multiple modules. Authors who rely on their own memory of which modules changed may inadvertently publish a mix of old and new content; the automated refresh makes that scenario impossible by treating the entire course as a single unit to be synchronized before output.

Taken together, the reasons for using the publish feature come down to three practical benefits. First, it consolidates multiple modules into one browsable experience. A learner who completes one module and wants to proceed to the next does not need to locate a new file or navigate to a separate URL — the site's structure handles the transition seamlessly. This reduces cognitive overhead for learners and removes the need for authors to communicate file-access instructions alongside course content.

Second, the publish feature bundles assembly and content refresh into a single action, which compresses what would otherwise be a multi-step manual process into one operation. Authors do not need to remember to refresh before assembling, or to assemble before uploading. A single publish command handles the sequence in the correct order every time, which reduces both the time required to release a course update and the likelihood that a step will be skipped under deadline pressure.

Third, the feature delivers a consistent output format regardless of how the course evolves over time. Whether a course grows from three modules to fifteen, or whether an author restructures the module order mid-project, the published site always conforms to the same structural template. This predictability makes the course easy to maintain: authors know what to expect from the output, and learners encounter the same navigational conventions each time they access the site. Consistent output also simplifies any downstream processes — such as hosting, accessibility review, or LMS integration — because those processes can rely on the published site always being organized the same way.

In practice, authors who understand these four aspects of the publish feature — what it assembles, how it uses index files, when and why it refreshes content, and what benefits it provides — are equipped to publish confidently, diagnose problems when they arise, and make deliberate choices about when and how often to run a publish during a course development cycle.
