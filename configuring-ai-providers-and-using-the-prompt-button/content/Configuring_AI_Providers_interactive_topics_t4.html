Understanding That There Is No Per-Task Provider Assignment

▶

One of the most important things to understand about how PreseMaker handles AI-powered content generation is that there is exactly one provider doing all of the work at any given time. Every feature that calls on artificial intelligence — whether it is generating module topics, writing learning outcomes, building slide content, drafting text lessons, creating quizzes and assignments, producing interactive activities, writing narration scripts, or aligning content to standards — is handled by a single, unified provider selection. That selection lives in one place: the Active AI Provider dropdown inside Settings. Nothing else in the application controls which provider is used, and no task is ever silently routed somewhere else.

This design is deliberate, and understanding it will save you significant troubleshooting time. The sections below explain exactly what the single-provider rule means in practice, what per-task assignment was, why it no longer exists, and how to correct some common misconceptions that arise — particularly for users who worked with older versions of the application.

The Single-Provider Rule

The Active AI Provider dropdown in Settings is the one and only place where a provider is selected for use inside PreseMaker. Whichever provider is chosen there — for example, OpenAI, Anthropic, or Google — becomes the provider for every AI task the application performs during that session. There is no secondary provider waiting in reserve, no fallback that takes over when the primary provider is slow or temporarily unavailable, and no mechanism that quietly uses a different provider for certain kinds of requests.

To make this completely concrete, consider everything PreseMaker can generate on your behalf:

  • Module topics and subtopics — the structural outline of a course module
  • Learning outcomes — measurable objectives tied to module content
  • Slide content — text, bullet points, and layout suggestions for individual slides
  • Text lessons — longer-form written explanations of a topic
  • Quizzes — questions, answer choices, and correct-answer logic
  • Assignments — task descriptions and rubric suggestions
  • Interactive activities — drag-and-drop, matching, scenario-based, and similar formats
  • Narration scripts — spoken-word text that accompanies slides or lessons
  • Standards alignment — mapping content to curriculum or competency frameworks

Every item on that list is handled by the same active provider. If you have selected OpenAI in the dropdown, OpenAI processes all of those requests. If you switch to Anthropic, Anthropic processes all of them from that point forward. The list never gets split across providers.

What Per-Task Assignment Means — and Why It Does Not Exist in PreseMaker

Per-task assignment refers to a configuration model in which different types of AI work are individually mapped to different providers. In such a system, an administrator might open a settings panel and see something like a routing table: one row for slide generation pointing to Provider A, another row for quiz generation pointing to Provider B, and so on. Each task type has its own provider selection.

PreseMaker has no such routing table. There is no per-task dropdown, no task-type configuration screen, and no way to direct one category of content generation to one provider while directing another category to a different provider. The application simply does not contain those controls. A few specific scenarios that are not possible — and that users sometimes ask about — are worth naming explicitly:

  • You cannot configure slide generation to use GPT-4o while quiz generation uses Claude. Both go to the single active provider.
  • You cannot assign narration to a provider that is better at natural language while assigning standards alignment to a provider that is better at structured data. Both go to the single active provider.
  • There is no concept of a "default provider for unassigned tasks." Because tasks are never individually assigned in the first place, there is nothing to fall back on. One provider covers everything.

This is not a limitation that can be worked around through advanced settings or configuration files. It is the intended architecture of the current version of PreseMaker.

Why the Feature Was Removed

An earlier version of PreseMaker did support per-task provider assignment. That version allowed different task types to be routed to different AI providers, which sounded flexible in theory but created a consistent and frustrating class of problem in practice.

The core issue was a mismatch between the API key a user believed was active and the key that a specific task actually required. Consider a typical failure scenario under the old model:

  • A user enters an API key for Provider A and confirms it works by generating a few slides successfully.
  • Behind the scenes, quiz generation has been mapped — perhaps by a previous user or by a default setting the user never noticed — to Provider B.
  • The user attempts to generate a quiz. The request fails.
  • The user assumes the API key is invalid, re-enters it, and tries again. It fails again — because the key is for Provider A, and the quiz task is trying to reach Provider B, for which no valid key has been entered.

From the user's perspective, the system appeared to be ignoring a valid API key, or the error message pointed at a provider the user had never intentionally configured. Diagnosing this required understanding the routing table, which most users were unaware existed. The result was support burden, user frustration, and wasted time.

Removing per-task assignment eliminated that entire class of configuration error. When there is only one active provider, an API failure is unambiguous: something is wrong with the one key or the one provider currently selected. There is no hidden routing to investigate, no secondary key to check, and no provider mismatch to untangle. The simplification made errors faster to diagnose and easier to resolve.

Correcting Common Misconceptions

Because per-task assignment existed in an older version of PreseMaker, some users carry forward assumptions from that version that no longer apply. The following misconceptions come up often enough to address directly.

  • Misconception: "I need to configure each task type separately." This was true in the older version. It is not true now. The single Active AI Provider selection covers all task types automatically. There are no per-task settings to configure.
  • Misconception: "There must be a hidden or advanced setting that re-enables per-task routing." There is not. The feature is fully removed from the application — not hidden behind a toggle, not accessible via a configuration file, not available in any admin or developer mode. It does not exist in the current version.
  • Misconception: "My API failures might be caused by tasks being routed to a provider I haven't configured." Under the single-provider model, this cannot happen. Every AI task goes to the active provider. If a task fails, the cause is related to the one active provider — the key may be invalid, the account may have insufficient credits, the provider's API may be experiencing an outage, or there may be a network issue. There is no second provider involved.
  • Misconception: "Switching the active provider only changes it for certain tasks." Switching the Active AI Provider dropdown changes it for all tasks, immediately. From the moment you save a new provider selection, every subsequent AI request in PreseMaker goes to that new provider.

Practical Implication: One Key Is All You Need

The most immediate practical consequence of the single-provider model is straightforward: entering a valid API key for one provider in Settings is sufficient to enable every AI-powered feature in PreseMaker. You do not need to obtain keys from multiple providers, you do not need to configure keys for different task types, and you do not need to do anything beyond selecting a provider and entering its key.

You may choose to enter API keys for more than one provider. Doing so gives you the flexibility to switch the active provider whenever you want — for instance, if you want to compare output quality between providers, or if one provider's service is temporarily degraded and you want to move to another. But having multiple keys entered does not mean multiple providers are ever used simultaneously. Only the one currently selected in the Active AI Provider dropdown is active at any moment.

Switching providers is a single action: change the Active AI Provider dropdown to the desired provider and save. From that point forward, all AI tasks — every item on the list above — use the newly selected provider. The transition is complete and immediate; there is no partial switchover or task-level override to manage.

To illustrate the contrast between the old model and the current one, the table below summarizes the key differences:

Aspect Old Per-Task Model Current Single-Provider Model
Provider selection location Multiple dropdowns, one per task type One dropdown: Active AI Provider in Settings
Number of providers active at once Potentially many (one per task type) Exactly one
API keys required One per provider assigned to at least one task One (for the single active provider)
Failure diagnosis Complex — must check which provider a failing task was routed to Simple — every failure points to the one active provider
Switching providers Update each task-type assignment individually Change one dropdown; all tasks update immediately
Risk of key/provider mismatch High — easy to leave a task mapped to a provider with no valid key None — one key covers every task

Understanding this table — and internalizing the shift from the old model to the current one — resolves the vast majority of configuration questions that arise around AI provider setup in PreseMaker. There is one provider, selected in one place, handling everything. That simplicity is the point.
