Understanding and Responding to Generation Failures

▶

When PreseMaker sends a request to an AI provider — whether to generate slide content, rewrite text, or produce images — there is a meaningful chain of dependencies between your application, your network, your account credentials, and the provider's own infrastructure. Any link in that chain can break, and when it does, PreseMaker encounters what is called a generation failure. Understanding why these failures happen, how PreseMaker communicates them to you, and what concrete steps you can take to resolve them is essential for working confidently and efficiently within the application.

Generation failures are not arbitrary or mysterious. They fall into a small set of well-defined categories, each with its own cause and its own resolution path. PreseMaker is designed to surface these failures explicitly and give you direct access to the tools you need to fix them — but it will never silently work around the problem for you. That design choice puts you in control and ensures you always know the real state of your provider connections.

Common Causes of Generation Failures

Before you can fix a generation failure, you need to understand what triggered it. There are four primary categories of failure, and recognizing which one you are dealing with is the first step toward a resolution.

The most frequently encountered cause is a missing or invalid API key. Every AI provider — whether that is OpenAI, Anthropic, Google, or another service — requires an API key to authenticate your account and authorize your requests. This key acts like a password specific to your application usage. If the key has never been entered in PreseMaker's Settings, the provider has no way to verify who is making the request and will reject it outright. Similarly, if a key was entered but has since been revoked by the provider, replaced by a new key in your provider account dashboard, or simply typed incorrectly, authentication will fail even though a key appears to be present. This is one of the most common causes of failure for new setups and after any account changes on the provider's side.

A second common cause is hitting a rate limit. AI providers enforce limits on how many requests you can make within a given time window — for example, a certain number of requests per minute, or a certain number of tokens processed per day. These limits vary by provider and by the tier of your subscription. When your usage exceeds the allowed threshold, the provider responds with a rate-limit error rather than fulfilling the request. This is not a malfunction; it is an intentional enforcement mechanism. Rate limits reset automatically after the time window expires, but if your usage patterns regularly push against the ceiling, you may need to consider upgrading your account tier with the provider.

A third category is network problems. PreseMaker communicates with provider APIs over the internet, which means any interruption to your network connection — a dropped Wi-Fi connection, a VPN that is blocking outbound requests, a firewall rule, or transient internet instability — can prevent the request from reaching the provider's servers at all. In these cases, the failure is not caused by anything wrong with your credentials or your account; the request simply never arrived, or the response never returned. Network problems can be intermittent and may resolve themselves, but they can also require deliberate troubleshooting of your connection or network configuration.

The fourth category is model or endpoint errors. Each task in PreseMaker is configured to use a specific AI model offered by the assigned provider — for example, a particular version of GPT or Claude. If that model has been deprecated and is no longer available, if the model identifier in your configuration is misspelled or references a version that does not exist, or if the provider is experiencing an outage on that specific endpoint, PreseMaker will receive an error from the provider indicating that the requested resource is unavailable. These errors often require you to update your configuration to reference a currently available and supported model.

The table below summarizes these four failure categories alongside their typical indicators and initial resolution directions:

Failure Category What Causes It Typical Indicator Initial Resolution Direction
Invalid or Missing API Key Key not entered, revoked, expired, or mistyped Authentication failure message Correct or replace the API key in Settings
Rate Limit Exceeded Too many requests in a given time window Rate limit or quota exceeded message Wait for reset or upgrade account tier
Network Problem Connection interrupted, VPN, firewall, instability Connectivity or timeout error Check network, VPN, and firewall settings; view log
Model or Endpoint Error Deprecated model, incorrect model ID, provider outage Model unavailable or endpoint error Update model configuration in Settings

How PreseMaker Responds to a Failure

When a generation request fails, PreseMaker's behavior is deliberate and consistent: it surfaces the failure to you immediately through a failure dialog. It does not silently retry the request with a different provider, and it does not attempt any automatic fallback. The provider that was assigned to the task at the time of the failure remains responsible for that task until you explicitly take action to either fix the configuration or reassign the task.

This behavior is intentional. Silent retries or automatic fallbacks might seem convenient in the short term, but they obscure real problems — you might not realize that a key has become invalid, that you are consistently hitting rate limits, or that a model has been deprecated. By surfacing every failure explicitly, PreseMaker ensures you remain aware of the state of your provider connections and can make informed decisions about how to respond. The failure dialog is not an obstacle; it is a diagnostic tool.

It is also worth understanding the implication of the no automatic fallback design. If you have configured multiple providers in PreseMaker, a failure with Provider A does not cause PreseMaker to automatically route the task to Provider B. Each task has a specific assigned provider, and that assignment holds until you manually change it. This means your other providers remain exactly where you configured them, and your task assignments remain predictable and intentional.

Interpreting the Failure Dialog

The failure dialog that PreseMaker presents is designed to be immediately actionable. Rather than showing a raw technical error code and leaving you to decipher it, the dialog translates the provider's response into a plain-language explanation that corresponds directly to one of the known failure categories. For example, an authentication failure will be identified as such — you will not simply see an HTTP 401 status code without context.

The dialog tells you the nature of the error. This means you will know immediately whether the problem is that your credentials were rejected, that you have hit a usage ceiling, that a connection could not be established, or that the specified model is unavailable. This direct correspondence between what the dialog says and the known failure categories makes diagnosis straightforward — you do not have to guess what went wrong.

Critically, the dialog also presents multiple resolution options inline. You do not need to dismiss the dialog, remember what went wrong, manually navigate to Settings, and then try to recall what you needed to change. The dialog keeps you in context and gives you direct pathways to take action. This reduces the friction between identifying a problem and resolving it.

Resolution Options Offered by the Dialog

The failure dialog provides three primary resolution options, each suited to a different failure scenario:

  • Open Settings: This option takes you directly to the PreseMaker Settings panel where your provider configurations are managed. From there, you can review the current configuration for the provider that failed, check which model is specified, confirm that the provider endpoint is correct, or update any other configuration details. This is the appropriate route when you suspect a misconfiguration — for instance, an incorrect model name or an endpoint that has changed.
  • Add a new API key: This option provides a focused pathway to enter or replace an API key, which is particularly useful when the existing key is known to be invalid or expired. Rather than navigating through the full Settings interface to find the key field, this shortcut brings you directly to the point of action. For authentication failures, this is typically the fastest resolution path.
  • View the log: This option opens the detailed error log, which contains the raw output from the failed request. Logs are especially valuable when the cause of a failure is not immediately clear from the dialog's description — particularly for network issues or endpoint errors where the specific error message from the provider can point you toward the exact problem. If you need to report a problem or diagnose something unusual, the log is your primary source of ground-truth information.

Fixing the Underlying Cause and Retrying

The failure dialog guides you to a resolution path, but actually fixing the problem requires taking the appropriate action based on the failure category. Once you have taken action, you must manually retry the generation — PreseMaker will not re-attempt the request on its own after a failure, regardless of what you have changed.

If the failure was caused by an invalid or missing API key, the resolution is to correct or replace the key. Open Settings (or use the direct shortcut from the dialog), locate the provider that failed, and update the API key field with a valid key from your provider account dashboard. Once the key is saved, retry the generation. If the key is valid and properly entered, the authentication error will not recur.

If the failure was caused by a rate limit, you have two options depending on the urgency of your work. The simplest option is to wait for the rate limit window to reset — most providers reset limits on a per-minute or per-day basis, and the provider's documentation will tell you exactly how long to wait. If you are doing high-volume work and consistently hitting rate limits, the longer-term solution is to upgrade your account tier with the provider to access a higher request quota. Once the limit has reset or your tier has been upgraded, manually retry the generation.

If the failure was caused by a network problem, start by confirming that your internet connection is active and stable. If you use a VPN, check whether it might be blocking outbound requests to the provider's API endpoint — some VPN configurations restrict certain types of traffic. If you are behind a corporate or institutional firewall, verify that the provider's API domain is not blocked. The detailed log can help here, as it may reveal whether the request timed out, was refused, or never received a response. Once your connectivity is restored or your network configuration is corrected, manually retry the generation.

If the failure was caused by a model or endpoint error, open Settings and review the model specified for the task that failed. Confirm that the model name matches a currently available model offered by the provider — providers update their model offerings regularly, and a model that was available when you first configured the task may have been deprecated. Consult the provider's documentation or dashboard to identify the correct current model identifier, update the configuration in Settings, and then manually retry the generation.

Manually Reassigning the Task to a Different Provider

Sometimes the fastest path forward is not to fix the failing provider but to route the task to a different provider that is currently working. This is particularly useful in situations where the failing provider is experiencing an outage, where you are waiting for a rate limit to reset, or where resolving the credential problem will take time you do not want to spend right now.

To do this, open Settings and locate the specific task type that failed. PreseMaker allows different task types — such as text generation, summarization, or image generation — to be assigned to different providers independently. Within the task's configuration, change the assigned provider from the one that failed to a provider that is currently configured and functional. Save the change, then return to your work and retry the generation. PreseMaker will now send the request to the newly assigned provider instead of the one that failed.

It is important to understand that this manual reassignment is the only mechanism by which a task can be routed to a different provider. There is no automatic fallback, no priority list of providers that PreseMaker works through on its own. The assignment you set in Settings is definitive until you change it again. This means that if you reassign a task to work around an outage, you may want to revisit the assignment later once the original provider is restored — or you may decide that the new assignment is preferable and leave it as is. Either way, the decision is yours, and PreseMaker will honor whatever configuration you have set.

To illustrate the end-to-end process, consider a practical example. Suppose you are working on a presentation and you trigger a generation that fails with an authentication error. The failure dialog appears and tells you the request could not be authenticated. You click the option to add a new API key, enter the updated key from your provider dashboard, and save it. You then manually retry the generation — this time, the request succeeds. Your work continues without having to navigate away from your presentation context any more than necessary, because the dialog kept you oriented and gave you a direct path to the fix.

In a different scenario, suppose the failure dialog reports a rate limit error late in your workday and you cannot afford to wait for the limit to reset. You open Settings from the dialog, find the affected task type, and reassign it to a second provider whose credentials you have already configured. You retry the generation immediately using the new provider and continue working. The original provider's rate limit will reset overnight, and you can reassign the task back if you prefer — but for now, your work is unblocked.

These workflows highlight the core design philosophy behind PreseMaker's failure handling: transparency over convenience. Every failure is visible, every failure has an identifiable cause, and every resolution is something you initiate deliberately. This gives you a clear, honest picture of how your AI provider integrations are functioning and keeps you in full control of how tasks are routed and retried.
