How PreseMaker Routes Tasks to Providers

▶

Every time PreseMaker runs a task — generating a slide outline, writing speaker notes, creating imagery, or any other AI-driven operation — it needs to know which provider to send that task to. The mechanism it uses to make that decision is called routing. Understanding how routing works in PreseMaker is essential for getting predictable results, managing costs, and knowing exactly what to do when something goes wrong. The routing model is deliberately simple and deterministic: one task type always maps to exactly one provider, the decision is made immediately when the task is triggered, and there are no hidden layers of logic running in the background.

At the foundation of PreseMaker's routing system is the default provider. Think of the default provider as the catch-all handler for any task type that has not been given a specific, explicit assignment. When you first configure PreseMaker and connect your AI providers, you designate one of those providers as the default. From that point on, any task that runs without a dedicated per-task assignment will be sent automatically to the default provider — no additional configuration required on your part.

This matters for a practical reason: PreseMaker supports a wide range of task types, and it is entirely normal to configure specific assignments for only a handful of them while leaving the rest unassigned. Without a default provider, those unassigned tasks would have nowhere to go. The default provider ensures that every task has a valid handler, even tasks you have never thought about configuring individually. Setting a thoughtful default — typically a capable, general-purpose provider you trust for quality and reliability — means PreseMaker can operate fully even with a minimal configuration.

Beyond the default, PreseMaker allows you to configure per-task provider assignments. A per-task assignment is a direct mapping between one specific task type and one specific provider. When an assignment exists for a task type, that assignment takes complete precedence over the default provider for that task type, and only that task type. Every other task type is unaffected and continues to route however it was previously configured — either to its own specific assignment or to the default.

Per-task assignments are managed in PreseMaker's Settings, where you will find a list of recognized task types alongside a selector for each one. Any provider you have already connected and configured will appear as an option. This setup gives you fine-grained control over how your provider resources are used. For example, you might assign a fast, low-cost provider to a high-volume task like bullet-point generation, while reserving a slower but higher-quality provider for a task like executive summary writing where output quality is the priority. The ability to optimize on a task-by-task basis — for cost, speed, or quality — is the primary reason per-task assignments exist.

To see how the default and per-task assignments work together, consider a concrete example. Suppose you have connected three providers — Provider A, Provider B, and Provider C — and made the following configuration:

Task Type Specific Assignment Provider That Runs It
Slide outline generation Provider B Provider B
Speaker notes Provider C Provider C
Image prompt creation None Provider A (default)
Title suggestions None Provider A (default)
Translation None Provider A (default)

In this example, Provider A is the default. Slide outline generation and speaker notes have explicit assignments to Provider B and Provider C respectively. All remaining task types — image prompt creation, title suggestions, translation, and any others not listed — fall through to Provider A automatically. The logic PreseMaker applies when any task fires is straightforward: does this task type have a specific assignment? If yes, use it. If no, use the default. That is the entire decision tree.

A critical aspect of PreseMaker's routing design is that one task type maps to exactly one provider at any given time. There is no concept of shared routing, split routing, or load balancing across providers for a single task type. When PreseMaker resolves which provider to use, it performs a single, immediate lookup — it finds the assignment for the task type (or the default), and it sends the task there. There is no runtime evaluation of provider availability, no comparison of response times, and no weighing of options. The decision is made once, instantly, and executed.

Related to this is the absence of any priority ranking between providers. PreseMaker has no concept of a "first choice" or "second choice" provider for a given task. You cannot configure a ranked list such as "try Provider A first, then Provider B, then Provider C." The routing system simply does not have that concept. Every routing decision is binary: either a specific assignment exists and is used, or the single default provider is used. There is no ordering, no weighting, and no preference hierarchy among your connected providers.

This also means there is no automatic fallback between providers. If the assigned provider for a task experiences a failure — the API returns an error, the provider is temporarily unavailable, a quota is exceeded, or any other problem occurs — PreseMaker does not silently retry the task with a different provider. Instead, PreseMaker surfaces a failure dialog, informing you that the task could not be completed. The outcome is a visible, explicit failure, not a transparent retry that might mask which provider is actually handling your work.

The implication for users is important: resolving a provider failure always requires a deliberate action on your part. You have two paths available. First, you can address the underlying cause of the failure — for instance, checking your API key, reviewing your account quota with the provider, or waiting for the provider's service to recover — and then re-run the task. Second, if you want to continue working immediately using a different provider, you can go into Settings, update the assignment for that task type to point to a different provider, and then re-run the task. Either way, the decision about which provider handles your work remains yours, made explicitly, rather than being made quietly in the background by PreseMaker's routing logic.

The overall design philosophy behind PreseMaker's routing model is transparency and predictability. Because routing is deterministic — a lookup with no branching beyond "specific assignment or default" — you always know which provider will handle a given task before you run it. Because there is no automatic fallback, you always know that a failure with Provider X means Provider X was the one that failed, not that the system already tried Providers Y and Z without telling you. This makes it straightforward to audit your provider usage, manage costs accurately, and troubleshoot problems without ambiguity about what happened behind the scenes.
