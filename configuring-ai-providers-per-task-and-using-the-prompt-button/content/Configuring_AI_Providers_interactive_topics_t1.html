Introduction to AI Providers in PreseMaker

▶

PreseMaker integrates artificial intelligence into its authoring workflow by connecting to external AI providers through API keys. These providers supply the language model intelligence that powers every automated content generation feature inside the application. Before configuring any provider, it helps to understand precisely what PreseMaker asks these providers to do, which providers are supported, how credentials are protected, and how the application decides which provider handles a given request. Each of these dimensions is covered in full below.

What PreseMaker Uses AI Providers For

Every AI task that PreseMaker performs is strictly text-based. There is no image generation, no image recognition, no computer vision, and no audio synthesis delegated to an AI provider. When PreseMaker calls an external model, it is always sending a text prompt and expecting a text response — nothing more.

This matters because some AI platforms offer a broad suite of capabilities, and it would be easy to assume PreseMaker exploits all of them. It does not. The integration is deliberately narrow: only the text-generation endpoint of a provider is ever used. What changes across different authoring tasks is the content of the prompt and the structure of the expected response, not the fundamental nature of the call.

The range of authoring tasks that trigger an AI call is wide. Examples include:

  • Generating quiz questions and answer choices for a knowledge check
  • Writing assignment instructions and grading criteria
  • Drafting slide narration scripts that accompany course content
  • Producing learning outcomes or course objectives
  • Suggesting or refining activity descriptions and scenario content
  • Aligning content to educational standards

Because every one of these tasks is text-in / text-out, configuring an AI provider means you are unlocking the full breadth of PreseMaker's generation features in a single step. Understanding this also sets accurate expectations: swapping one AI provider for another will not change whether a task is possible — all four supported providers are capable of text generation — but it may change the quality, tone, or style of the output, since each underlying model has different strengths.

The Four Supported AI Providers

PreseMaker currently recognizes four external AI providers. Each represents a distinct company and underlying language model family:

Claude Anthropic Claude (various versions)
Gemini Google Gemini model family
GPT-4o OpenAI GPT-4o
Mistral AI Mistral AI Mistral model family

A critical practical point: you do not need API keys for all four providers. Having a valid, active key for at least one provider is entirely sufficient to use PreseMaker's AI features. Many users work with a single provider throughout their entire authoring practice and never configure the others. You can add additional keys at any time if your organization later obtains access to a second or third provider and you want the option to switch between them.

Each provider's API key is entered separately in PreseMaker's Settings area. The fields are independent — entering a key for GPT-4o has no effect on the Claude field, and vice versa. Keys can be added, updated, or removed individually without disturbing the configuration of the other providers.

How API Keys Are Stored and Secured

API keys are sensitive credentials. A leaked key can result in unauthorized charges to your account or misuse of your provider quota. PreseMaker addresses this through a combination of encryption and storage isolation.

When you save an API key in PreseMaker's Settings, the application immediately encrypts it using Windows DPAPI (Data Protection API). DPAPI is a built-in Windows cryptographic service that ties encrypted data to the specific Windows user account that encrypted it. This means the ciphertext stored on disk is useless to anyone who does not have access to that same Windows session — even if they obtain the file directly.

The encrypted key is written to a file named app_settings.json, located under your local user profile directory. This file is not a shared or network location; it lives on the individual user's machine, within their profile.

Two important security consequences follow from this design:

  • Keys are never embedded in course files. When you publish or export a course package, no API credentials travel with it. A colleague who opens your exported course in their own PreseMaker installation will not inherit your provider configuration.
  • Keys are never shared with any repository. Whether you use a local folder, a shared network drive, or a version-controlled repository to store your course source files, the app_settings.json file stays on your machine and is not part of the course project structure.

A practical consequence of this architecture is that every user who needs to run AI features must configure their own API key in their own installation of PreseMaker. There is no central credential store that a team can point to. If three authors on a team all need AI generation, each person must obtain an API key from the relevant provider and enter it in their own copy of the application. This is by design — it keeps each person's billing and usage tied to their own credentials.

The Active AI Provider Setting

Having one or more API keys stored in PreseMaker is a prerequisite, but it does not by itself tell the application which provider to use. That decision is made through the Active AI Provider dropdown in the Settings area.

The dropdown lists the four supported providers. Selecting one designates it as the provider responsible for all AI work PreseMaker performs from that point forward. The selection is global — it applies across every project you open and every content type you work with.

Changing the active provider takes effect immediately. There is no restart required. As soon as you save the new selection, the very next AI request PreseMaker makes will be routed to the newly selected provider. This makes it straightforward to experiment: you can generate a quiz with one provider, switch the active provider in Settings, generate a second quiz, and compare the outputs side by side.

Note what happens if you select a provider for which you have not yet entered an API key: PreseMaker does not fail. It automatically uses whichever provider does have a key on file. If you have entered only one key, PreseMaker selects that provider for you, so a single key is all the configuration required. This selection is based on which keys exist — it is not a retry after a failure. What PreseMaker cannot do is authenticate when no provider has a key at all, so the one thing you must do is enter at least one valid key, in the field belonging to the provider that issued it.

One Provider Handles Every Task — No Per-Task Routing

A question that often arises from experienced users is whether different AI tasks can be sent to different providers — for example, using GPT-4o for quiz generation because of its strong reasoning, while using Claude for narration because of its natural prose style. In the current version of PreseMaker, the answer is no.

There is no routing table. There is no per-task provider dropdown. There is no concept of a "default provider for unassigned tasks." The active provider handles everything: narration, outcomes, quizzes, activities, standards alignment, assignments, and any other text generation feature the application offers. If you want a different provider to handle a particular task, the only way to achieve that is to switch the active provider in Settings, perform the task, and then switch back if needed.

This single-provider model was introduced deliberately. In an earlier design that allowed per-task provider assignment, users encountered a category of configuration errors that proved difficult to diagnose — for instance, a task failing silently because it was assigned to a provider whose key had expired, while the key for the user's preferred provider was valid and active. By collapsing all routing to a single selection, PreseMaker eliminates that class of problem entirely. When something goes wrong with an AI request, there is exactly one provider to inspect.

When planning your PreseMaker configuration, the practical guidance is straightforward: choose the provider whose overall text quality best fits your authoring needs, enter its key, set it as active, and expect every AI feature in the application to use it consistently. If your needs change or you want to compare providers, the active provider can be switched at any time with immediate effect.
