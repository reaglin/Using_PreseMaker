Publishing a Course Website with GitHub Pages

▶

Once you have built your course in PreseMaker, the next step is making it accessible to learners anywhere in the world. GitHub Pages is a free hosting service provided by GitHub that turns the files stored in a repository into a publicly reachable website. PreseMaker integrates this entire workflow — from packaging your course content into a deployable website to pushing it live — directly into its own interface. You do not need to open a terminal, write git commands, or navigate GitHub's hosting settings manually. What you do need is a GitHub account and an empty (or dedicated) repository ready to receive your course. With those two prerequisites in place, PreseMaker takes care of everything else.

Understanding the end-to-end process before you begin saves time and prevents confusion. At a high level, the journey looks like this:

  • You export the course from PreseMaker, which packages it into a complete set of website files.
  • You connect that course to a GitHub repository by supplying its URL inside PreseMaker.
  • You trigger a publish action inside PreseMaker, which pushes the exported files to the repository.
  • GitHub Pages detects the new files and serves them at a stable public web address.
  • Whenever you update the course, you re-export and push again; the live site updates automatically.

Each of these stages is explained in full detail below.

Exporting the Course Website Before Publishing

Before any file can be placed on the internet, PreseMaker must first transform your course project into the kind of content a web browser can read and display. This is what the export function does. When you initiate an export from inside PreseMaker, the application bundles everything — slides, media, navigation logic, styling, and any interactive elements — into a self-contained folder of standard web assets: HTML files, CSS stylesheets, JavaScript, and any images or other media your course uses.

This exported package is significant for two reasons. First, it is entirely self-contained: a learner's browser does not need PreseMaker installed or running in order to view the course. Second, it is exactly what GitHub Pages will serve. GitHub Pages is not a content-management system that processes or re-renders your files; it is a static file host. Whatever files you push to the repository are the files learners receive, byte for byte. That means the quality and completeness of the export directly determine what the learner experiences.

You initiate the export from within PreseMaker's menus — no external tools, no manual file copying, and no knowledge of web development are required at this stage. PreseMaker handles the assembly of all assets. The result is a folder on your local machine that represents the full course website and is ready to be handed off to GitHub.

Connecting the Course to a GitHub Repository

With exported files ready, the next step is telling PreseMaker where on GitHub those files should live. You do this by providing the remote repository URL — the address GitHub assigns to your repository, typically in the form https://github.com/your-username/your-repository-name.git — inside PreseMaker's publishing or settings panel.

Once you supply that URL, PreseMaker stores it as part of the course's configuration. This is an important convenience: you only have to enter the repository address once per course. On every subsequent session, PreseMaker already knows which repository belongs to which course, so you can move straight to pushing updates without re-entering connection details. PreseMaker also records the timestamp of the most recent successful push, giving you a clear at-a-glance indicator of whether your live site is current.

It is worth understanding what a GitHub repository is, if you are new to the concept. Think of it as a project folder stored on GitHub's servers, with built-in version history. Every time you push new files, GitHub records what changed and when. For the purposes of GitHub Pages, the repository is simply the storage location from which GitHub reads and serves your website files. You create the repository on GitHub's website (github.com) before connecting it in PreseMaker — this is the one action that takes place outside PreseMaker.

A few practical notes about the repository you create:

  • It should be set to public visibility if you want learners to access the course without logging in to GitHub. GitHub Pages on free accounts requires a public repository to serve a site publicly.
  • You can name the repository anything meaningful — for example, intro-to-python-course or safety-training-2025. The name becomes part of the public URL, so a descriptive, lowercase, hyphenated name is a good habit.
  • If you create the repository with a README file, make sure PreseMaker's export files will not conflict with it; starting with a completely empty repository is often the simplest approach.

Publishing Through PreseMaker Rather Than GitHub's Website

Once the repository is connected, publishing is triggered entirely from within PreseMaker. You do not visit GitHub's website, navigate its Settings panel, enable GitHub Pages, or choose a branch — PreseMaker handles all of that on your behalf when you use its publish action.

Under the hood, what PreseMaker performs is a git push: it takes the exported website files and sends them to the remote GitHub repository, placing them on the branch that GitHub Pages is configured to watch. Git is the version-control system that powers GitHub, and a push is the operation that transfers your local file changes to the remote server. Normally, using git requires opening a terminal (the command-line interface on your computer) and typing commands such as git add ., git commit -m "message", and git push origin main. PreseMaker abstracts all of this away. You click a button; PreseMaker executes the equivalent commands internally. Note that PreseMaker runs the Git program installed on your computer rather than replacing it, so Git for Windows must be installed — if it is not, PreseMaker will tell you that git is not on the system PATH and point you to the download page.

This design decision has a meaningful impact on who can publish a course. An instructional designer, subject-matter expert, or educator can share their work with the world without learning version-control workflows or command-line tools. The technical barrier is reduced to: have a GitHub account, create a repository, paste the URL into PreseMaker, and click publish.

The Live Public Web Address

After the first successful push, GitHub Pages activates and assigns a public URL to the repository. The format of that URL depends on how the repository is named and who owns it:

Repository type URL pattern Example
Standard project repository https://username.github.io/repository-name/ https://jsmith.github.io/intro-to-python-course/
Special user/organization site (repo named username.github.io) https://username.github.io/ https://jsmith.github.io/

For most course authors, the first pattern applies. The URL is constructed automatically by GitHub based on your account name and repository name — you do not choose it manually, but you can predict it before pushing. Once active, this address is fully public: anyone with the link can visit the course in their browser without signing in to GitHub, without installing software, and without any special credentials. This makes the link ideal for sharing in an email, a learning management system, a syllabus, or a social media post.

The URL is also stable. As long as the repository exists and GitHub Pages remains enabled, the address does not change, even after you push many rounds of updates. You can confidently share the link with learners at the start of a term and know it will remain valid throughout. The only scenarios that would break the URL are deleting the repository, renaming it (which changes the URL), or explicitly disabling GitHub Pages in the repository's settings.

Pushing Updates to the Published Site

A published course is rarely static. You may correct errors discovered after launch, add new content, revise existing slides, or update media. PreseMaker's publishing model is designed to make this iterative process straightforward.

The update workflow mirrors the initial publish:

  • Make your changes inside PreseMaker's course editor.
  • Export the course again, which regenerates the complete website file package reflecting your latest changes.
  • Use PreseMaker's push action to send the updated files to the GitHub repository.

When GitHub Pages detects that new files have been pushed to the watched branch, it begins serving those updated files. There is typically a short delay — usually under a minute, sometimes a few minutes — between when the push completes and when the public URL reflects the changes. This is GitHub's infrastructure rebuilding the served site. After that brief period, any learner who visits the URL receives the current version of the course. No cache-clearing or special steps are required on the learner's end for new visitors; returning visitors may occasionally need to refresh their browser if the browser has cached the older version.

PreseMaker's record of the last push timestamp is a small but useful feature in this context. If you are uncertain whether a particular round of edits has been published, you can check that timestamp against your memory of when you last exported and pushed. If they match, the live site is current. If the timestamp predates your most recent edits, you know another export-and-push cycle is needed.

Together, these capabilities — guided export, remembered repository connections, one-click publishing, a stable public URL, and simple update pushes — form a complete self-service publishing pipeline. Authors who focus on content rather than infrastructure can still deliver polished, professionally hosted course websites to learners anywhere in the world.
