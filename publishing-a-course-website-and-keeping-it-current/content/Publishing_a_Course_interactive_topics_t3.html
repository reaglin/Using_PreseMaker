How Publishing Refreshes Module Content

▶

When you work inside PreseMaker, every change you make to a module — adding a new lesson, editing an existing page, or removing outdated material — is saved to the authoring environment, but those changes do not automatically reach the version of the course that learners browse. The publish feature is the bridge between your working files and the live, browsable website. A central part of what publish does is refresh each module's HTML index, ensuring that the snapshot learners see is perfectly aligned with the content you have actually authored. Understanding this mechanism in depth helps you manage your course confidently and avoid the common pitfall of assuming that saved changes are the same as published changes.

At the heart of every module in PreseMaker is a dedicated HTML index file. Think of this file as a curated table of contents that is specific to its module. It aggregates every content item belonging to that module — lessons, resources, assessments, media pages — and represents them as a coherent, navigable collection. When a learner arrives at your course website and clicks on a module, it is this HTML index that their browser loads first. The index is therefore the authoritative entry point for the module; everything a learner sees or can navigate to from that module's landing page flows through it. Because the index plays such a central role in the learner experience, keeping it current is not optional — an outdated index can expose broken links to deleted content, hide newly added lessons entirely, or present a module as incomplete when it is actually fully built out.

The question then becomes: what causes PreseMaker to update this file? The answer is the publish action. Initiating a publish sends a signal to PreseMaker to begin a systematic scan of your course. During this scan, PreseMaker examines each module and compares its current content state to whatever was recorded the last time a publish was run. Any differences — a new topic added, a lesson title changed, a resource deleted — are captured during this content refresh step. If you have never published at all, the HTML index either does not yet exist in its final form or reflects only an initial scaffold. If you published last week and have made ten edits since, the live HTML index still reflects last week's state until you publish again. This is why instructors who are actively developing a course should treat publishing as a regular, deliberate step rather than a one-time action.

Once PreseMaker has identified what has changed, it proceeds to regenerate the HTML index for any module that is out of date. The regeneration process reads the current, authoritative state of every content item within the module and writes a new index file from scratch based on that state. The newly generated file completely replaces the previous version — there is no merging or patching. This wholesale replacement is important because it eliminates edge cases like stale hyperlinks pointing to content that was deleted, or index entries that were reordered but not fully updated. The result is a clean, accurate HTML index that faithfully represents every content item currently in the module and nothing that has been removed.

Consider a practical example. Suppose you built a module called Introduction to Data Analysis with three lessons last month and published the course. This week you added two new lessons on statistical methods and deleted one lesson that was a duplicate. If a learner visited the site right now, they would see three lessons — the state from last month. When you run publish, PreseMaker scans the module, detects the two additions and one deletion, and regenerates the HTML index with four lessons (the two original non-duplicate lessons plus the two new ones). The deleted lesson's link vanishes, and both new lessons appear correctly linked. The learner who visits after your publish sees exactly what you intended.

PreseMaker also follows a carefully defined sequence during the publish operation: it refreshes and regenerates every module's HTML index first, and only after all indexes are current does it compile those indexes into the broader, browsable course website. This ordering is deliberate and critical. If PreseMaker compiled the website before refreshing the indexes, it might incorporate a mix of current indexes (for modules you had just edited) and stale indexes (for modules you had not recently touched but that were still pending a refresh). The resulting site would be inconsistent — some modules accurate, others not. By completing all index refreshes before beginning the website build, PreseMaker guarantees that the compilation step works exclusively with up-to-date inputs. Learners who arrive at the freshly published site can trust that every module landing page they navigate to is current.

The table below summarizes the sequence of events during a publish operation and the role each step plays:

Step What PreseMaker Does Why It Matters
1 — Content Scan Scans all modules and identifies content that has changed since the last publish Ensures no additions, edits, or deletions are overlooked before updating begins
2 — Index Regeneration Regenerates the HTML index for every module whose content is out of date Replaces stale index files with accurate, current representations of module content
3 — Website Compilation Compiles all refreshed module indexes into the complete browsable course website Guarantees the live site is built entirely from current module data, with no mixed states

The practical impact of this process on both instructors and learners is significant. From a learner's perspective, every visit to a module landing page after a publish presents a list of only valid, current content. There are no dead links to lessons that were removed, no missing entries for lessons that were added but not yet reflected. The module landing page functions as a reliable map of what the module actually contains at the moment of the last publish.

From an instructor's perspective, the publish feature provides a controlled deployment mechanism. You can make a series of edits, reviews, and revisions in the authoring environment over days or weeks without those intermediate, potentially incomplete states being visible to learners. When you are satisfied with the state of the course, a single publish operation brings everything current simultaneously. This means you can confidently share a link to the published site or formally deploy it to a class, knowing that every module reflects your latest intentional changes rather than a half-finished intermediate state.

One important boundary condition to keep firmly in mind: any changes made after the most recent publish will not appear on the live site until publish is run again. This is not a flaw — it is an intentional safeguard — but it is a common source of confusion. Instructors sometimes add a lesson, check the live site immediately, and wonder why the new lesson is not visible. The answer is always the same: the HTML index for that module has not yet been regenerated because publish has not been triggered since the addition was made. The fix is straightforward: run publish again. Developing a habit of publishing after any meaningful round of edits, and communicating expected publish schedules to learners if the course is live, will prevent nearly all confusion related to content visibility.

  • The HTML index is the module's authoritative landing page — learners encounter it before any individual piece of content, making its accuracy foundational to the learner experience.
  • Publishing is what triggers the refresh — saving content in the authoring environment alone does not update the live site; the publish action initiates the scan, regeneration, and compilation sequence.
  • Regeneration is a full replacement — PreseMaker writes a brand-new HTML index rather than patching the old one, which eliminates stale links and missing entries cleanly.
  • Refresh always precedes build — the defined sequence ensures the website compilation step never operates on a mix of current and outdated module indexes.
  • Changes after the last publish are invisible until the next publish — instructors must re-publish to surface any new edits, deletions, or additions to learners on the live site.
