Method 3: Importing from a File or Repository

▶

When working within PreseMaker, there are several ways to bring a module into your working environment. The third method — importing from a file or a remote repository — is specifically designed for situations where a module already exists as a packaged, distributable unit. Rather than building a module from scratch or pointing PreseMaker to a folder you have manually organized on your filesystem, this approach lets you receive, retrieve, and register a module through a guided intake workflow. It is the most practical path when modules are being shared between team members, distributed across organizational environments, or pulled from a centralized hosting source. Understanding when and how to use this method will save time, reduce setup errors, and ensure that modules are consistently registered in a state that is immediately ready for use.

What Is the Import Method?

The import method is a structured workflow within PreseMaker that accepts a module from an external source — either a packaged archive file stored locally or a remote repository accessible via a URL — and registers it inside the Module Manager so it becomes available for content generation and editing. The key distinction from other methods is that the module already exists in a complete, self-contained form before the import begins. You are not creating or configuring the module's structure; you are receiving it and letting PreseMaker process it into your environment.

This approach is particularly valuable in collaborative or distributed contexts. When a module has been authored by one team and needs to be reused by another, packaging and importing is far more reliable than manually transferring individual files. PreseMaker handles the intake process internally, so the person importing the module does not need to understand the module's internal folder structure or know exactly where files should be placed on disk. The import workflow abstracts those details and ensures the module lands in a valid, registered state.

Another important characteristic of this method is that it supports distribution across different installations. A module packaged on one machine can be imported on another without requiring those machines to share a network drive or have identical directory structures. This makes the import method the right tool for cross-environment reuse, such as moving a module from a development environment to a production one, or sharing work between colleagues who are in different offices or organizations.

When to Use This Method

Choosing the correct import method depends on where the module currently exists and how it arrived in your possession. The file-and-repository import method is the right choice in three primary scenarios.

  • A colleague has shared a packaged module file with you. When a team member exports or packages a module from their own PreseMaker installation and sends it to you — via email, a shared drive, a file transfer service, or any other delivery mechanism — you will receive an archive file. This file is not meant to be manually unpacked and placed somewhere on your filesystem. Instead, you use the import workflow to hand it directly to PreseMaker, which processes and registers it correctly.
  • You need to pull a module from a remote repository. Organizations often maintain hosted repositories of approved or standardized modules. These repositories may be internal company servers or externally hosted platforms. Rather than downloading and then manually placing files, the repository-based import points PreseMaker directly at the source, and the application handles the retrieval and registration in a single operation.
  • The module has not yet been extracted or placed in a local directory. If you have a packaged module file but have not yet unzipped or organized its contents into a local folder, the import method is preferable to the folder-based method. There is no need to manually prepare the filesystem. PreseMaker reads the archive or repository source and performs the extraction and registration itself.

Conversely, if you already have a module's folder structure present and organized on your local machine or network drive, the folder-based method may be more direct. The import method shines precisely when the module is in a packaged or remote state that has not yet been integrated into your local environment.

Supported Source Types

The import workflow supports two distinct source types, each suited to a different distribution scenario. Both ultimately produce the same result — a registered, available module inside the Module Manager — but they differ in where the module originates and how PreseMaker retrieves it.

Source Type Description Typical Use Case
File-based import A packaged module archive stored on your local computer or an accessible network drive. You browse to the file's location and select it within the import workflow. Receiving a module from a colleague, importing a module from a USB drive or shared folder, or importing a previously exported backup of a module.
Repository-based import A remote location — such as a hosted organizational repository — identified by a URL or connection string. PreseMaker connects to the repository and retrieves the module directly. Pulling standardized or approved modules from a team's central module library, fetching updates to a shared module, or onboarding a new installation with an established module set.

In the file-based scenario, the archive is typically a compressed package that bundles everything the module needs — its configuration, content definitions, metadata, and any associated assets. PreseMaker knows how to read this package format, so the user simply provides the file path and lets the application do the rest.

In the repository-based scenario, the user provides a URL or connection reference pointing to a hosted location. PreseMaker contacts that location, downloads the necessary module data, and registers it — all within the import workflow. This is especially useful when an organization wants to maintain a single source of truth for its modules and ensure all team members are working from the same, up-to-date version.

Steps to Import a Module

The import process follows a clear, sequential workflow. Each step is handled within the PreseMaker interface, and no manual filesystem manipulation is required at any point.

  • Open the Module Manager. Navigate to the Module Manager within PreseMaker. This is the central hub for all module-related operations. From here, locate and select the option to import a module from a file or repository. This option initiates the import workflow.
  • Choose your source type. The import workflow will prompt you to specify whether you are importing from a local file or from a remote repository. Select the appropriate option based on where your module currently resides. If you are importing from a file, you will be asked to browse to the archive on your computer or network drive and select it. If you are importing from a repository, you will be prompted to enter the repository's URL or connection details.
  • Provide the required path or URL. Supply the exact location of the module. For a file-based import, this means navigating to and selecting the packaged archive file. For a repository-based import, this means entering a valid URL or repository address. Accuracy here is important — an incorrect path or URL will prevent PreseMaker from locating the module.
  • PreseMaker validates and processes the source. Once you confirm the source, PreseMaker inspects the provided file or repository to verify that it contains a valid, compatible module. This validation step catches issues such as corrupt archives, incompatible module versions, or unreachable repository addresses before any changes are made to your environment. If validation succeeds, PreseMaker proceeds to extract and register the module.
  • The module is registered and becomes available. After successful processing, the module appears in the Module Manager alongside any other modules already present in your environment. It is now in an active, registered state and is ready for content generation or further editing, exactly as if it had been created locally or added through another method.

The linear nature of this workflow is intentional. Each step confirms that the previous one succeeded before proceeding, which minimizes the risk of partially registered or broken modules entering your environment.

Role of the Module Manager in This Method

The Module Manager is not simply a passive display of available modules; it is the active hub through which the entire import workflow is initiated, monitored, and confirmed. Every aspect of the file-and-repository import method runs through it, which keeps the process centralized and consistent.

When the import begins, the Module Manager provides the interface controls that allow you to specify your source type and input the required path or URL. As PreseMaker processes the import, the Module Manager reflects the current status — whether validation is in progress, the module is being retrieved, or the registration has been completed. This visibility is important in repository-based imports, where network latency might mean the process takes a moment longer than a local file import.

Once the import finishes successfully, the Module Manager displays a confirmation and the newly imported module appears in the module list. At this point, the module has transitioned from an external, packaged state to an internal, registered state within PreseMaker. It is no longer sitting in an archive on your desktop or waiting in a remote repository — it is fully integrated into your PreseMaker environment and subject to all the same operations as any other module: content generation, editing, exporting, and so on.

By centralizing the import workflow within the Module Manager, PreseMaker ensures that there is a single, authoritative record of which modules are registered and available. This prevents the kind of ambiguity that can arise when modules are added by manually placing files in directories, where the application may or may not be aware of their presence until a separate discovery or refresh step is performed. With the import method, registration is explicit and immediate.
