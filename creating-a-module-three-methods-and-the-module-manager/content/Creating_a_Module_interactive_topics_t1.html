Overview of Module Creation in PreseMaker

▶

PreseMaker organizes all authoring work around a fundamental unit called a module. Before you can generate content, configure outputs, or collaborate with a team, you must first understand what a module is, why the application offers several different ways to create one, and how all of those pathways converge inside the Module Manager. This overview sets the conceptual foundation that makes every subsequent step in PreseMaker feel purposeful rather than procedural.

A module in PreseMaker is a self-contained project container. Think of it as a dedicated folder of intent: it bundles together the configuration that describes what you want to produce, the source materials that feed the generation process, and the output content that results from that process. Because everything belonging to a single learning or presentation unit lives inside one module, projects stay organized even as they grow in complexity. Equally important, modules are portable — you can move a module folder between machines, hand it off to a colleague, or archive it without losing any of the context needed to reproduce or extend the work. This self-contained nature is not accidental; it reflects a deliberate design choice to make PreseMaker projects as independent of any particular machine or environment as possible.

Modules can come into existence in three fundamentally different ways, and understanding the distinction between them is the first real decision point every PreseMaker author faces:

  • Created from scratch using AI generation. PreseMaker scaffolds the entire module structure automatically, generating configuration and initial content based on prompts or parameters you supply. No pre-existing files are required.
  • Added from an existing folder on disk. If you have already organized content locally — perhaps a collection of slide decks, transcripts, or reference documents arranged in a folder hierarchy — PreseMaker can register that folder as a module without disturbing its structure.
  • Imported from an external file or repository. A module that was built in another PreseMaker workspace, packaged for distribution, or stored in a version-controlled repository can be brought into your current workspace through an import process.

The existence of three separate methods is not redundancy; each method addresses a genuinely different situation an author might face. An author who is starting from zero — no outline, no slides, no notes — benefits most from letting PreseMaker's AI generation method scaffold the structure automatically. The AI path removes the blank-page problem: it produces a working module skeleton that the author can then refine, rather than requiring the author to build that skeleton manually. This is the fastest on-ramp for net-new projects.

An author who has already done significant local organization is in a different position. Suppose a subject-matter expert has spent weeks assembling reference PDFs, recording short video clips, and arranging everything into a logical folder hierarchy on their laptop. Rebuilding that structure inside a brand-new PreseMaker module would be wasted effort. The add from disk method solves this by registering the existing folder with PreseMaker, effectively telling the application "treat this folder as a module." The content and its organization are preserved exactly as the author left them.

Teams working across multiple machines or drawing on shared repositories face a third challenge: consistency and reuse. When one team member finishes building a module and wants every other member to work from the same baseline, emailing files or manually copying folders is error-prone. The import method provides a controlled pathway. A module can be exported as a portable package or pushed to a repository, then pulled cleanly into any other workspace. This is also the mechanism that supports version control workflows, where modules live in a git repository and are checked out as needed.

Regardless of which creation method you choose, all three pathways lead to the same destination: the Module Manager. The Module Manager is PreseMaker's central dashboard for module-level work. It provides a unified view of every module currently available in your workspace — you can see their names, statuses, and configurations side by side. More importantly, the Module Manager is where the application communicates the state of each module. A module that was just created or just registered from disk starts in a minimal state: it exists, but it may be missing configuration details or source materials that content generation requires. The Module Manager surfaces those gaps clearly, guiding you from that empty or partial state toward a fully configured module that is ready for generation.

This progression — from created to configured to ready — is an important mental model. Creating a module, by any of the three methods, is only the first step. What the creation step accomplishes is establishing the module's identity and location within your workspace. What happens after creation depends on which method was used and how complete the initial state is:

  • An AI-generated module may arrive relatively complete, with scaffolded content already in place, but it will still typically need review and possible configuration adjustments before final generation runs.
  • A module added from a local folder will have its files present but may need PreseMaker-specific configuration added — for example, specifying which files are source materials and what output format is desired.
  • An imported module may be fully configured from its originating workspace, in which case it could be ready to generate immediately, or it may need local path adjustments if it references resources at specific locations.

The Module Manager signals readiness visually, so you always know whether a module still needs attention or whether you can proceed to content generation. This signal-and-status design means you do not have to memorize a checklist; PreseMaker tracks the requirements and tells you when they have been met.

To make the choice between creation methods concrete, consider three brief scenarios:

  • Scenario A — The new author. A training developer is building a compliance course on a topic they have never covered before. They have no existing files, no outline, and no source documents. They open the Module Manager, choose the AI generation method, supply a topic description and a few parameters, and PreseMaker returns a fully scaffolded module with an initial content structure ready to review. Total time before first content exists: minutes.
  • Scenario B — The organized expert. A senior engineer has a folder on their desktop containing forty pages of technical documentation, a dozen diagrams, and an annotated outline they wrote over several months. They want to turn that material into a PreseMaker module without reorganizing anything. They open the Module Manager, choose the add-from-disk method, point it at their folder, and PreseMaker registers the module. Their existing file structure is preserved; they simply add the PreseMaker configuration layer on top.
  • Scenario C — The distributed team. A content team at a large organization maintains a shared repository of approved PreseMaker modules. A new team member needs to work on an existing module. They open the Module Manager, choose the import method, point it at the repository package, and the module appears in their local workspace fully configured and ready to edit. Any changes they make can later be exported and pushed back to the repository.

These scenarios illustrate that the three methods are not alternatives competing for the same use case — they are complementary tools designed for genuinely different starting conditions. Recognizing which scenario matches your current situation is the practical skill this overview is meant to build. With that recognition in place, the detailed steps for each method become much easier to follow, because you already understand why you are taking them.

In summary: a PreseMaker module is a portable, self-contained container for configuration, source materials, and output content. Three creation methods exist because authors begin work from three meaningfully different starting points — no prior assets, locally organized assets, and externally sourced assets. All three methods are accessible from the Module Manager, which also tracks each module's progress from its initial empty or minimal state to the fully configured state where content generation can begin. Understanding this structure and these options is the essential first step before working with any specific creation workflow in PreseMaker.
